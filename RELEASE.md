# Release runbook

One tag, one pipeline, and a rehearsal path that proves the pipeline before anything is public.

## Version policy

`Cargo.toml` is the single source of version truth. Everything else — the npm manifests, the
release asset names, the tag — is generated from it or checked against it, and CI fails on the
disagreement rather than noticing later:

| Thing | How it is kept in step |
|---|---|
| npm `package.json` versions | generated by `scripts/write-manifests.mjs` from Cargo.toml |
| build matrix ↔ npm packages | both read `scripts/targets.mjs`; nothing lists targets twice |
| tag ↔ crate version | `release.yml` plan job refuses a `vX` tag when Cargo.toml says `vY` |
| asset ↔ its claimed target | `scripts/verify-asset.mjs` reads the ELF/Mach-O header, and execs the binary (directly or through qemu) to read `--build-info` |

SemVer within 0.x, as `CHANGELOG.md` states: a minor bump may rename a `--json` field; a patch bump
may not. `schema_version` in the document is the machine-readable counterpart — bump it whenever the
shape changes, because a consumer cannot read a changelog.

## Cutting a release

```sh
# 1. bump the version where it lives
$EDITOR Cargo.toml
node scripts/write-manifests.mjs      # regenerates every package.json
node scripts/check-versions.mjs       # proves they agree
cargo test --all-targets && cargo clippy --all-targets -- -D warnings

# 2. move "Unreleased" in CHANGELOG.md under a dated heading for the new version

# 3. commit, push, and confirm CI is green before tagging
git commit -am "release: 0.3.0" && git push origin master
gh run list --limit 1

# 4. rehearse the release pipeline with no public effect
gh workflow run release.yml           # builds all five targets, packs npm tarballs, uploads run artifacts
gh run watch

# 5. tag. This is the step that makes it visible.
git tag -a v0.3.0 -m "necropsy 0.3.0"
git push origin v0.3.0
gh run list --workflow release.yml
gh release view v0.3.0
```

A tag containing `-` (e.g. `v0.3.0-rc.1`) is published as a **prerelease**.

`workflow_dispatch` on `release.yml` runs the identical build and packaging and stops at the last
step: it uploads the assets to the *run*, and creates no release and no tag. Run it before step 5,
because the first execution of a release workflow is not the place to discover the linker flag was
wrong.

## Assets

Per target, `necropsy-<version>-<cargo-target>.tar.gz` containing `necropsy`, `LICENSE`,
`README.md`, plus a matching `.sha256` and an aggregate `SHA256SUMS.txt` that covers the tarballs
and the npm packages. Archives are built with `--sort=name --mtime=@0 --owner=0 --group=0` so two
runs of one commit produce identical bytes: a checksum difference then means a content difference,
not a timestamp.

Targets: `x86_64-unknown-linux-gnu`, `x86_64-unknown-linux-musl`, `aarch64-unknown-linux-gnu`,
`aarch64-apple-darwin`, `x86_64-apple-darwin`.

**There is no Windows build, on purpose.** The offline suite spawns the binary through `assert_cmd`
with POSIX assumptions, and nothing in this tree has ever run on Windows. Shipping an unverified
`win32` package would be a claim, not a feature.

## npm

The bare name `necropsy` on npm belongs to someone else's package — a Node core-dump debugger,
`necropsy@1.0.3`, last touched 2022 — so distribution uses the scope:

- `@0xcyrildev/necropsy` — the launcher (`bin/necropsy`) and nothing else.
- `@0xcyrildev/necropsy-<os>-<cpu>[-<libc>]` — one per target, each holding exactly one binary at
  `bin/necropsy`, selected by npm's `os`/`cpu` fields as `optionalDependencies`.

Nothing downloads at install time. There is no `postinstall`, no fetch, and no checksum-verified
curl of a release asset: the binaries arrive as ordinary npm tarballs, so an install touches the
registry and nothing else. The trade is six packages to publish instead of one, and it buys the
removal of a fetch-and-exec step from every user's machine — the same reasoning that keeps the CI
Foundry install to a pinned, hashed tarball rather than a pipe-to-shell.

Publishing is opt-in because it needs the scope first:

```sh
# one time, on npm: create the @0xcyrildev organization (or scope your user), then either add an
# Automation token as the NPM_TOKEN secret, or — preferred — configure each package as a GitHub
# Actions trusted publisher so no long-lived secret exists at all.
gh workflow run publish-npm.yml -f version=0.3.0
```

`publish-npm.yml` downloads the npm tarballs from the GitHub Release for that version, verifies
them against `SHA256SUMS.txt`, and publishes with `--provenance`. It is `workflow_dispatch`-only,
guarded by an `npm` environment: no push and no tag can publish a package.

The launcher refuses to run a platform package whose version differs from its own, so a partially
upgraded tree says so instead of exec'ing a binary nobody tested against this wrapper.

## crates.io

`crates.io` has no `necropsy` crate, so the Rust name is free and `cargo install necropsy` is the
plain path once published:

```sh
cargo publish --dry-run   # checks the package contents; verify no AGENTS.md in the file list
cargo publish
```

`AGENTS.md` is gitignored, so it is excluded from the package; `cargo package --list` is the check
that proves it, and the dry run above is the moment to look.
